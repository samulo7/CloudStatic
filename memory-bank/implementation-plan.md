# CloudStatic 基础功能实施计划

## 目标

先完成最小可用闭环：上传图片 → 构建期处理图片 → 生成图片链接 → 写 MDX 文章 → 构建静态站点 → 部署到 Cloudflare Workers Static Assets。

本计划给 AI 开发者使用。每一步小而具体。每一步都必须验证。禁止在执行计划时跳过测试。

## 全局约束

- 写任何代码前，先完整阅读 `CLAUDE.md`。
- 写任何代码前，先完整阅读 `memory-bank/@architecture.md` 和 `memory-bank/@game-design-document.md`；如果缺失，先创建基础版本并记录当前架构和产品目标。
- 保持模块化。不要创建单体巨文件。
- 不要把海量图片长期放进 `public/images/`。
- 图片二进制默认不进入 git history。
- 运行时保持静态优先，不引入 SSR、KV、D1、R2、运行时图片优化。
- React 只用于需要交互的 islands。
- 每完成重大阶段后，更新 `memory-bank/@architecture.md`。

## 阶段 3：图片处理基础

### 步骤 3.1：定义图片输入与输出目录

指令：

- 建立本地或 CI 输入目录：`content-assets/incoming-images/`，用于临时接收原始图片。
- 建立处理后输出目录：`content-assets/processed-images/`，用于生成部署前图片资产。
- 输出路径必须匹配 `/images/[year]/[month]/[hash].webp` 和 `/images/thumb/[hash]_400w.webp`。
- Astro 构建后，通过独立脚本命令把 `content-assets/processed-images/images/` 复制到 `dist/images/`；不要使用 Astro postbuild 钩子，不要配置 Wrangler 额外 assets 目录。
- 不把长期图片资产放进 `public/images/`。

验证：

- 输入目录存在或可由脚本创建。
- 输出目录结构符合约定。
- `.gitignore` 排除图片输入和处理后输出目录中的二进制图片。

### 步骤 3.2：实现图片哈希命名流程

指令：

- 使用图片内容计算 SHA-256。
- 取前 16 位作为基础文件名。
- 相同图片重复处理时复用同一输出名。
- 不使用原始文件名作为最终 URL 文件名。

验证：

- 同一张图片处理两次，输出文件名一致。
- 两张不同图片输出文件名不同。
- 原始文件名包含中文、空格、特殊字符时，最终文件名仍安全。

### 步骤 3.3：实现 WebP 转换

指令：

- 对 PNG/JPG/JPEG 输入生成 WebP 主图。
- 保留合理质量设置。
- 记录图片宽度、高度、格式、大小。
- 不在运行时做图片转换。

验证：

- PNG 输入生成 WebP。
- JPG 输入生成 WebP。
- 不支持的文件类型被跳过或报出明确错误。
- 生成文件可被浏览器打开。

### 步骤 3.4：实现 400w 缩略图生成

指令：

- 为每张主图生成 400px 宽缩略图。
- 小于 400px 的图片不要被放大。
- 缩略图路径使用 `/images/thumb/`。

验证：

- 大图缩略图宽度为 400px。
- 小图缩略图不被放大。
- 缩略图文件名与主图 hash 对应。

### 步骤 3.5：实现 manifest 生成

指令：

- 生成 `manifest.json`。
- 每条记录包含：hash、主图 URL、缩略图 URL、宽度、高度、格式、文件大小、创建时间。
- manifest 只记录元数据，不内嵌图片内容。
- manifest 可提交入仓库。

验证：

- 处理一张图片后 manifest 新增一条记录。
- 重复处理同一图片不产生重复记录。
- manifest JSON 格式有效。
- URL 路径与实际输出文件一致。
